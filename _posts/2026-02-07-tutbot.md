*TUTbot* (short for tutorial robot) is a mobile robot I'm building to get a better understanding of teleoperation, autonomous navigation, perception and simulation. It runs ROS 2 Jazzy on a Raspberry Pi 5, and I went through it one layer at a time: hardware, URDF, simulation, ros2_control, kinematics, odometry, sensor fusion and finally mapping and localization. This post is a condensed version of the full docs in the repo.

### Raspberry Pi Setup

The Pi gets SSH, a static IP and ROS 2 Jazzy, plus serial port permissions (`sudo usermod -a -G dialout $USER`). A PS4 controller is paired over Bluetooth with `bluetoothctl` (pair → trust → connect), and a udev rule in `/etc/udev/rules.d/81-event.rules` lets non-root applications read the joystick input events:

```
SUBSYSTEM=="input", KERNEL=="event*", GROUP="raspberry", MODE="0660"
```

The workspace is built with `colcon build --parallel-workers 2`, since the Pi runs out of resources with more workers.

### RPLIDAR C1

![RPLIDAR C1](/assets/tutbot/rplidar-c1.png)

The C1 uses time of flight and triangulation to measure distance:

- 12 m range, 0.05 m blind zone
- 10 Hz (600 RPM) scan rate, 0.72° angular resolution
- 5000 samples/s, 30 mm accuracy
- UART at 460800 baud, 230 mA

It connects through a UART to USB-C converter and shows up at `/dev/ttyUSB0`, then it's just `ros2 launch sllidar_ros2 view_sllidar_c1_launch.py`. I built a 30×30×10" box to test it, and it measured the walls accurately at the expected ~74 cm.

## URDF and Visualization

The Unified Robot Description Format (URDF) is an XML description of the robot's links, joints and visuals. It gives all the ROS tools (RViz, Gazebo, robot_state_publisher) one code-independent, human-readable description of the robot's geometry.

![URDF base_footprint and base_link](/assets/tutbot/urdf-vis-1.png)

`base_footprint` is the origin frame and `base_link` is the main body. The wheels are added as links connected through `continuous` joints, and the casters through `fixed` joints. URDF has two origins: the **link** origin places the visual mesh relative to the link frame, and the **joint** origin is the transform from the parent link to the child link. Rotating roll by 90° in each one gives very different results:

![Link origin rotation](/assets/tutbot/link-origin-rotation.png)

![Joint origin rotation](/assets/tutbot/joint-origin-rotation.png)

With all links and joints in place, the joint_state_publisher GUI can spin the wheels live in RViz:

![Joint state publisher GUI](/assets/tutbot/joint-pub.gif)

Under the hood, that's `robot_state_publisher` (with the xacro converted to XML and passed as the `robot_description` parameter), `joint_state_publisher_gui`, and RViz with the fixed frame set to `base_footprint` plus TF and RobotModel displays. I wrapped all of it into one `display.launch.py`.

## Gazebo Simulation

Gazebo needs two extra things in the URDF:

- **`<collision>`** shapes: meshes are expensive, so the wheels and casters use simple spheres.
- **`<inertial>`** properties for every link.

The physics parameters live in `bumperbot_gazebo.urdf.xacro`:

- `mu1` / `mu2` are the Coulomb friction coefficients in two directions. Setting them really high forces no slip, which isn't physical but guarantees traction.
- `kp` / `kd` are the contact stiffness and damping, which stop the wheels bouncing and oscillating.
- `minDepth` is the penetration needed before contact forces kick in, which filters out numerical noise.
- `maxVel` caps the velocity used to correct interpenetration.
- `fdir1` is the primary friction direction.

![Gazebo simulation of the robot](/assets/tutbot/gz-sim-1.png)

The world is the AWS RoboMaker small house:

![Small house world in Gazebo](/assets/tutbot/small-house.gif)

### Simulated Sensors

The IMU gets its own `imu_link` and fixed joint, plus the `gz-sim-imu-system` plugin. The sensor runs at 100 Hz with Gaussian noise: stddev 2e-4 on angular velocity and 1.7e-2 on linear acceleration, because accelerometers are a lot noisier than gyros. Gazebo topics aren't visible to ROS on their own, so a `ros_gz_bridge` parameter bridge forwards `/imu` (remapped to `/imu/out`) and `/clock`.

```python
gz_ros2_bridge = Node(
    package="ros_gz_bridge",
    executable="parameter_bridge",
    arguments=[
        "/imu@sensor_msgs/msg/Imu[gz.msg.IMU",
        "/clock@rosgraph_msgs/msg/Clock[gz.msgs.Clock",
    ],
    remappings=[("/imu", "/imu/out")]
)
```

![Simulated IMU data in PlotJuggler](/assets/tutbot/sim-imu.gif)

The LiDAR is simulated the same way with a `gpu_lidar` sensor: 360 samples and a 0.12 to 12 m range, matching the C1.

## ros2_control

ros2_control is a modular control framework that decouples the control logic from the hardware, so the same controllers can run on the simulator or the real robot.

```
 Controllers (diff_drive, velocity, ...)
        │  claim command/state interfaces
        ▼
 Controller Manager   – load/unload, lifecycle, deterministic update loop, services
        │  arbitration requests
        ▼
 Resource Manager     – owns hardware, tracks who claimed what, prevents conflicts
        │  state ▲   ▼ command
        ▼
 Hardware Interfaces  – left/right_wheel_joint: state = position, velocity
        │                                    command = velocity
        ▼  read() / write()
 Physical Hardware    – motors, encoders, IMU over UART / USB / CAN
```

- **Controller Manager** loads, configures and activates controllers (they're plugins) and runs them all at a fixed rate every cycle. It also makes sure no two controllers command the same interface.
- **Controllers** implement the control algorithms. `JointStateBroadcaster` is read-only and just publishes joint states, while `JointGroupVelocityController` commands velocities for a group of joints.
- **Hardware Interfaces** (System / Actuator / Sensor) expose shared read-only *state* interfaces and exclusive writeable *command* interfaces, and implement the low-level `read()`/`write()`.
- **Resource Manager** keeps the registry of all interfaces and tracks which controller owns which command interface.

To set it up, the Gazebo xacro loads `gz_ros2_control` (or `ign_ros2_control` on Humble, picked from `ROS_DISTRO` in the launch file). A new `bumperbot_ros2_control.xacro` declares both wheel joints with a velocity command interface (limited to ±1 rad/s) and position/velocity state interfaces. The controllers are configured in yaml:

```yaml
controller_manager:
  ros__parameters:
    update_rate: 100
    use_sim_time: true
    joint_state_broadcaster:
      type: joint_state_broadcaster/JointStateBroadcaster
    simple_velocity_controller:
      type: velocity_controllers/JointGroupVelocityController

simple_velocity_controller:
  ros__parameters:
    joints:
      - wheel_left_joint
      - wheel_right_joint
```

After spawning both controllers, `ros2 control list_hardware_interfaces` shows both wheel velocity interfaces as `[claimed]`, and publishing a `Float64MultiArray` to `/simple_velocity_controller/commands` moves the robot: `[1, 1]` drives straight and `[1, -1]` spins in place.

![Robot moving forward and then rotating in place](/assets/tutbot/ros2-control-test.gif)

## Kinematics

The pose of a differential drive robot on a plane is just **(x, y, θ)**. I started with turtlesim to get comfortable with topics, services and transforms.

![Turtlesim teleop](/assets/tutbot/turtlesim-teleop.gif)

![rqt graph of turtlesim and teleop nodes](/assets/tutbot/rqt-turtlesim.png)

`/teleop_turtle` publishes `Twist` messages on `/turtle1/cmd_vel` and `/turtlesim` subscribes to them. After spawning a second turtle with the `/spawn` service, `simple_turtlesim_kinematics.py` computes the transform between the two turtles:

```
t = [x2 − x1, y2 − y1]ᵀ            θ = θ2 − θ1

T = | cos θ   −sin θ   Tx |
    | sin θ    cos θ   Ty |
    |   0        0      1 |
```

![Translation vector and rotation matrix from turtle1 to turtle2](/assets/tutbot/t1-2.png)

### Differential Kinematics

With wheel radius *r*, wheel separation *l* and wheel speeds φ̇<sub>R</sub>, φ̇<sub>L</sub>, the body velocities are:

```
v = r/2 · (φ̇R + φ̇L)
ω = r/l · (φ̇R − φ̇L)

| v |   | r/2   r/2 | | φ̇R |              | φ̇R |   | 1/r    l/2r | | v |
| ω | = | r/l  −r/l | | φ̇L |     and      | φ̇L | = | 1/r   −l/2r | | ω |
```

The robot can't slide sideways (the nonholonomic constraint), so its body velocity is [v, 0, ω]. Rotating that into the world frame and combining it with the mapping above gives the **forward differential kinematics**, the Jacobian from wheel speeds to world pose rates:

```
| ẋ |   | r/2·cos θ   r/2·cos θ |
| ẏ | = | r/2·sin θ   r/2·sin θ | | φ̇R |
| θ̇ |   |   r/l         −r/l    | | φ̇L |
```

### Simple Speed Controller

`simple_controller.py` takes `wheel_radius` (0.033 m) and `wheel_separation` (0.17 m) as parameters (also exposed as launch arguments), subscribes to `bumperbot_controller/cmd_vel` and converts each command into wheel speeds for `simple_velocity_controller/commands` using the inverse of the conversion matrix:

```python
self.speed_conversion_ = np.array([[r/2, r/2],
                                   [r/l, -r/l]])   # → [[0.0165, 0.0165], [0.1941, -0.1941]]
```

## TF2

TF2 keeps track of all coordinate frames over time. **Static** transforms (sensor mounts, fixed joints) are published once on `/tf_static`, while **dynamic** transforms (robot motion, `odom → base_link`) are published continuously on `/tf` with timestamps.

`simple_tf_kinematics.py` publishes a static transform that puts `bumperbot_top` 0.3 m above `bumperbot_base`:

![Static TF in RViz](/assets/tutbot/tf2-static.png)

and a dynamic transform that moves `bumperbot_base` along x relative to `odom` in a 10 Hz timer:

![Dynamic TF in RViz](/assets/tutbot/tf2-dynamic.gif)

Rotation uses quaternions from `tf_transformations`: every tick multiplies the orientation by a 0.05 rad yaw increment, and after 100 ticks the increment is inverted so it spins back the other way.

```python
q = quaternion_multiply(self.last_orientation_, self.orientation_increment_)
...
if self.rotations_counter_ >= 100:
    self.orientation_increment_ = quaternion_inverse(self.orientation_increment_)
```

![Dynamic TF with translation and rotation](/assets/tutbot/tf2-dynamic-2.gif)

I also wrote a TF2 **listener**: a custom `GetTransform.srv` (frame_id, child_frame_id → TransformStamped, success) backed by a `Buffer` + `TransformListener` and `lookup_transform()`. `tf2_tools view_frames` and `tf2_echo` are really handy for debugging the frame tree.

![tf2_tools view_frames](/assets/tutbot/tf2-tools-view-frames.png)

## Odometry

Wheel speeds come from the change in joint position between two `JointState` messages (a forward finite difference, assuming the speed is constant over Δt):

```
φ̇ = (φ¹ − φ⁰) / (t₁ − t₀) = Δφ / Δt
```

Integrating the velocity equations over time gives the incremental pose update the controller runs on every joint state message:

```python
d_s     = (r * dp_right + r * dp_left) / 2
d_theta = (r * dp_right - r * dp_left) / l

self.theta_ += d_theta
self.x_     += d_s * np.cos(self.theta_)
self.y_     += d_s * np.sin(self.theta_)
```

That pose (θ converted to a quaternion) and the twist are published as a `nav_msgs/Odometry` on `bumperbot_controller/odom` with `odom` as the parent and `base_footprint` as the child frame. A small `simple_trajectory_plotter` node in `bumperbot_utils` appends every odometry pose to a `nav_msgs/Path` for RViz:

![Robot trajectory in RViz](/assets/tutbot/odometry-trajectory.png)

The same transform is broadcast with a `TransformBroadcaster`, so the whole robot model now moves around the `odom` frame in RViz:

![Odometry transform broadcast](/assets/tutbot/tf-odom-br.gif)

## Sensor Fusion

### Adding Noise

Real sensors and actuators are never perfect, so to test the robustness of everything downstream I made a `noisy_controller.py`. It runs alongside the simple controller and publishes to `/bumperbot_controller/odom_noisy` (`base_footprint_noisy` frame), with:

- Gaussian noise (σ = 0.005) on both wheel encoders
- a wheel radius error (+0.005 m, measurement error or wear)
- a wheel separation error (+0.02 m)

The errors are passed in as launch arguments and added to the real values through an `OpaqueFunction` in the launch file.

![Noisy vs clean odometry in PlotJuggler and RViz](/assets/tutbot/noisy-odom-1.gif)

Driving around with the joystick makes the drift really obvious: `base_footprint` is the clean odometry and `base_footprint_noisy` wanders off.

![Noisy vs clean odometry while driving](/assets/tutbot/noisy-odom-2.gif)

### Kalman Filter

A Kalman filter is a recursive estimator: it **predicts** the next state from a motion model, then **updates** that prediction with a measurement, weighting each by how uncertain it is. It's optimal for linear systems with Gaussian noise, and it's the simplest Bayesian filter.

My first one is one-dimensional: it fuses the noisy odometry's angular z (motion) with the IMU's angular z (measurement). It starts with a huge variance (1000) since it knows nothing at first, with a motion variance of 4.0 and a measurement variance of 0.5:

```python
def statePrediction(self):
    self.mean_     = self.mean_ + self.motion_
    self.variance_ = self.variance_ + self.motion_variance_

def measurementUpdate(self):
    self.mean_ = (self.measurement_variance_ * self.mean_ + self.variance_ * self.imu_angular_z_) \
                 / (self.variance_ + self.measurement_variance_)
    self.variance_ = (self.variance_ * self.measurement_variance_) \
                     / (self.variance_ + self.measurement_variance_)
```

![Kalman filtered odometry](/assets/tutbot/odom-kalman.gif)

### Extended Kalman Filter

To fuse the full state, I used `robot_localization`'s `ekf_node` at 30 Hz in 2D mode. It takes the x/y velocity from the noisy wheel odometry, and the yaw, yaw rate and x acceleration from the IMU (both in differential mode), and publishes `odom → base_footprint_ekf`. A static transform puts `imu_link_ekf` 0.103 m above the base, and an `imu_republisher` node re-frames the IMU data for it. The EKF tracks the ground truth a lot better than the raw noisy odometry:

![EKF based localization](/assets/tutbot/ekf.gif)

## Mapping and Localization

Everything uses the standard ROS frame chain **map → odom → base_link**:

- `odom` is smooth and continuous but drifts over time.
- `map` is fixed and doesn't drift, but its corrections can jump.
- `base_link` moves with the robot, and all the sensors are defined relative to it.

**Local localization** (odometry) provides `odom → base_link`, and **global localization** corrects the drift by providing `map → odom`.

### Odometry Motion Model

Any motion between two poses can be broken into a rotation, a translation and a second rotation:

```
x' = x + δtrans · cos(θ + δrot1)
y' = y + δtrans · sin(θ + δrot1)
θ' = θ + δrot1 + δrot2
```

To model uncertainty, each part gets zero-mean noise that scales with the motion:

```
δ̂rot1  = δrot1  − noise(α1·|δrot1| + α2·|δtrans|)
δ̂trans = δtrans − noise(α3·|δtrans| + α4·(|δrot1| + |δrot2|))
δ̂rot2  = δrot2  − noise(α1·|δrot2| + α2·|δtrans|)
```

- α1 is rotation noise from rotation, and α2 is rotation noise from translation.
- α3 is translation noise from translation, and α4 is translation noise from rotation.

`odometry_motion_model.py` draws 300 samples from this distribution (all α = 0.1) every step, and you can watch the uncertainty grow unevenly depending on how the robot moves. This is exactly what particle filters build on.

![Odometry motion model with uncertainty](/assets/tutbot/odom-model.gif)

### Speed and Separation Monitoring

`twist_mux` arbitrates between the velocity sources:

- Joystick commands have priority over keyboard commands, and a source that stops publishing times out and gets ignored.
- A **safety lock** at priority 255 (no timeout) overrides everything whenever `/safety_stop` is `true`.
- A `twist_relay` node converts between `Twist` and `TwistStamped` so all the pieces fit together.

`safety_stop.py` reads the LiDAR scan and puts the robot in one of three states:

- **FREE** (nothing nearby): runs at normal speed.
- **WARNING** (obstacle within 0.6 m): slows the robot down by triggering a `JoyTurbo` decrease action.
- **DANGER** (obstacle within 0.2 m): publishes `safety_stop = true`, which engages the lock and stops the robot completely.

When the area clears, it releases the lock and restores speed. It also publishes the warning and danger zones as RViz cylinder markers whose transparency changes with the state.

![Safety stop: the robot stops right before a collision](/assets/tutbot/safety-stop.gif)

![Warning and danger zones in RViz](/assets/tutbot/marker-vis.gif)

### Mapping with Known Poses

Before trying SLAM, I wrote my own occupancy grid mapper that assumes the pose is known (from the `odom → base_footprint` TF):

- **Grid:** 50 × 50 m with a 0.1 m resolution, every cell starting at a 0.5 prior.
- **Inverse sensor model:** each laser beam is traced from the robot to its endpoint with **Bresenham's line algorithm**. Cells along the ray are marked free (p = 0.35) and the endpoint is marked occupied (p = 0.9).
- **Log-odds update:** each cell is updated with `l += logodds(p) − logodds(prior)`, and the log-odds are converted back to probabilities when the map is published.

![Mapping with known poses](/assets/tutbot/mapping-with-known-poses.gif)

### AMCL

Adaptive Monte Carlo Localization localizes the robot on a known map with a particle filter: 500 to 2000 particles, a likelihood field laser model and the differential drive motion model, updating every 0.25 m or 0.2 rad of motion.

![Adaptive Monte Carlo Localization](/assets/tutbot/mapping-amcl.gif)

### SLAM

Doing mapping and localization at the same time is SLAM. I used `slam_toolbox`, which is factor graph based (Ceres solver), at a 5 cm resolution with loop closure turned on:

## Arduino to ROS

The first step towards running on the real robot was getting the Wemos talking to ROS over serial, in a `bumperbot_firmware` package (ament_cmake, so it can hold both Python and C++):

- **ROS → Arduino:** `simple_serial_transmitter.py` subscribes to `serial_transmitter` and writes each message to the board with pyserial (the port and baud rate, `/dev/ttyUSB0` @ 115200, are ROS parameters). The sketch turns the built-in LED on for a `1` and off for a `0`.
- **Arduino → ROS:** the sketch prints an increasing counter every second, and `simple_serial_receiver.py` reads lines in a 100 Hz timer and republishes them on `serial_receiver`.

```python
def timerCallback(self):
    if rclpy.ok() and self.arduino_.isOpen():
        data = self.arduino_.readline()
        try:
            data = data.decode("utf-8").strip()
        except:
            return
        msg = String()
        msg.data = data
        self.pub_.publish(msg)
```
